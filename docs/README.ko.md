## 어떤 문제를 다뤘나

암호화된 트래픽을 분석할 때 내용을 직접 읽는 대신, 패킷 길이·방향·도착 간격에 나타나는 패턴으로 앱과 서비스를 구분할 수 있는지 탐구했습니다. 모델 입력에는 페이로드, IP 주소, 포트를 사용하지 않습니다.

패킷 시퀀스의 관계를 학습하는 Transformer와 전체 플로우의 통계 정보를 결합했습니다. 시퀀스는 최대 128개 패킷이지만, 통계 피처 13개는 자르기 전 전체 플로우에서 계산합니다.

## 제가 맡은 역할

3인 팀에서 제공받은 패킷 시퀀스 CSV를 바탕으로 **AI 코딩 도구를 활용한 모델 구성, 반복 학습, 하이퍼파라미터 튜닝, 실험 비교와 성능 분석**을 담당했습니다. 원시 PCAP 수집과 초기 피처 추출은 개인 담당 범위로 주장하지 않습니다.

Random Forest와 Transformer를 실험하며 시퀀스 길이, 모델 규모, 통계 피처 결합, 손실 함수 설정 등을 검토했습니다. 초기와 최종 실험의 데이터·분할 조건이 달라 단순한 개선율로 제시하지 않습니다.

## 결과 해석

점수는 모델 선택에도 사용한 내부 검증셋 기준입니다. 데이터에 `from` 열이 없어 분할이 행 단위로 실행되므로, 세션 중복 차단이나 누수 방지를 단정할 수 없습니다. 독립 테스트 성능으로도 표현하지 않습니다.

저장된 리포트에서 라벨 76의 F1은 약 0.69로 전체 평균보다 낮았습니다. 데이터는 라벨당 312~413개여서 심한 클래스 불균형을 원인으로 단정하기 어렵습니다.

![성능이 낮은 클래스](../assets/class-performance.png)

다음 단계로 세션·수집 구간별 분할, 독립 테스트, 피처·손실별 비교 실험, 라벨 매핑과 설정을 포함한 체크포인트 패키징을 제안합니다.
